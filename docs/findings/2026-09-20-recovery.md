# September 20 deletion and recovery

Historical reconstruction, reviewed 2026-09-23. Primary sources remain immutable under `/mnt/avrana_media/recovery-20260920`: `RECOVERY-LEDGER.md`, `INCIDENT-REPORT.md`, `HANDOFF.md`, and `bookstack-live/COMPARISON.md`. This is a synthesis, not a copy of sensitive recovery records.

## Incident

The first observable deletion effects occurred at 2026-09-20 17:15:59 PDT (September 21 00:15:59Z). Most of `/home/cody` was deleted. An OOM kill at 17:16:48 followed the destructive effects; the evidence does not establish the deletion mechanism. Do not attribute the deletion to the OOM event as a proven cause.

The September 21 05:08Z forensic record found 43 missing bind mounts, representing 39 host paths across 24 of 40 containers. User systemd units/enablement, deployment source, virtual environments, timer scripts, tunnel configuration and service state were affected. The morning backup exposed approximately 14h45m of activity to loss.

Recovery used Git-hosted source, the verified 2026-09-20T09-34-23Z backup, validated surviving/deleted-open state, and limited reconstruction. `/mnt/root-recovery-snap` was created after deletion; it is evidence, not a pristine pre-incident root restore.

## BookStack

The BookStack service directory was deleted while containers continued using deleted inodes. A 41-table logical dump was rescued before stopping anything. Comparison with the morning dump found zero differing tables. Recovery restored from the verified backup and preserved the rescued dump.

Recorded checks: 41 tables, zero row-count mismatches, 12 books, 3 chapters, 72 pages, 3 shelves and 350 revisions; login, upload and status validation succeeded without reseeding. This supports no identified post-backup BookStack data loss at that recovery checkpoint. It does not prove that every subsequent edit is represented in the old export.

On this session's inspection both BookStack containers were running/healthy with zero recorded restarts. No API calls, SQL execution, new dumps, restarts, configuration changes or writes were performed against BookStack. Its existing export was parsed offline for documentation.

## Jellyfin

Recovery combined morning configuration with a newer rescued database and restored healthy operation. Current investigation confirms working-copy integrity but incomplete image assets. Both the golden archive's database and rescued database retain 3,768 image records, while the golden archive omits the metadata directory. See [the artwork finding](2026-09-23-jellyfin-artwork.md) for current counts and the repair decision. Do not replace the newer database merely to recover thumbnails.

Other recovered newer state included Seerr, Beszel, Shelfarr queue, CWA, Libation, Home Assistant storage, SABnzbd history, Libation status source and Speech-to-Phrase's lexicon. Some backup-only activity and untracked material were lost; exact private user records are intentionally not reproduced here.

## Preserve evidence

Earlier SQLite checks created sidecars and empty wrong-path databases inside preserved backup sets. Latest recovery instructions explicitly prohibit cleaning this contamination. Preserve both golden copies, rescued dumps/databases, lexicon copy, original manifests and notes. Their paths are references only; none of their data belongs in Git.

The incident demonstrates why container health and database ping cannot establish file persistence or restart safety. Future maintenance must reconcile bind inodes and deleted-open files before stopping services.
